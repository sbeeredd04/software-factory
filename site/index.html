01 / One approved outcome

One continuing loop. Clear ownership.

Ground the next priority, shape it into BMad epics and stories, and carry it through to a verified result. Feedback informs the next cycle; required evidence and review gates stay in place.

  1. Discover + prioritize

    Ground ideas and feedback in the project, affected assets and actual repository state. Choose the next useful outcome.

    ORCHESTRATOR + PROJECT CONTEXT

  2. BMad epics + stories

    Use BMad planning skills to structure the work, acceptance criteria and dependencies. Independently review the approach.

    BMAD PLANNING + INDEPENDENT REVIEW

  3. Build

    Staff the work with the expertise it needs. Implement, test and repair; parallelize independent work within actual host capabilities.

    ENGINEERS + HOST WORKERS

  4. Review + test

    Independently inspect the actual change and exercise affected behavior. Failed or unknown proof requires repair and fresh evidence.

    QA + REVIEWER + EVALUATOR

  5. Ship + verify

    Integrate behind required gates. Deliver within approved authority; verify deployed identity and the actual result.

    INTEGRATION OWNER + RELEASE

  6. Observe + improve

    Read authorized feedback within its source scope and window. Reconcile the evidence and feed the next eligible cycle.

    SCOPED OBSERVATION + ORCHESTRATOR

The human owns the boundaries.

At any phase, the agent weighs risk, affected assets and the autonomy you requested. Escalate unclear authority, consequential tradeoffs and decisions you reserved. Routine authorized work continues; configured checkpoints, actual permissions and proof gates remain binding. After a decision, resume the affected step.

02 / Features and failures

Progress includes the return path.

A failed test, uncertain effect or confirmed review finding is work to resolve. The same evidence standard holds from a new feature to a production signal.

A / Feature loop

From intent to an observed result.

  1. Ground the outcome, then plan BMad epics, stories and acceptance criteria.
  2. Review the plan; reconcile scoped GO.
  3. Claim work, implement, test and review.
  4. Independently prove effects on the actual HEAD.
  5. Integrate, prove the deployed identity and behavior.
  6. Use verified results and authorized feedback to prioritize the next eligible story.

↳ Failed or unknown proof → corrective work → fresh proof.

B / Bug loop

Evidence before a theory.

  1. Record the bug and preserve primary evidence.
  2. Reproduce safely; separate mechanism from hypothesis.
  3. Demonstrate no-fix closure, or plan a root-cause fix.
  4. Capture a failing regression; repair and review.
  5. Prove the original reproduction against the resulting artifact.
  6. Close with receipts and re-observe within approved access.

↳ Unknown cause → separating experiment. Recurrence → linked follow-up.

03 / Evidence has an address

“Done” deserves a receipt.

Accepted assertions come before implementation. Bind test and effect evidence to the exact subject, then have someone independent inspect what actually happened.

Eval first.

Use fail-to-pass cases for the new behavior and pass-to-pass cases for what must survive. Calibrate qualitative rubrics with known good and bad canaries.

One master board.

Per-story records hold live story status. Dashboards and the lifecycle graph are derived views. Claims describe assignment; they do not establish a worker is running.

A graph of recorded facts.

Trace requirements, code surfaces, claims, receipts, findings and deployed identities. Provenance exposes stale subjects and missing proof. A declared link or bare commit identity does not prove a shipped effect.

09 / Before your first lap

The practical questions.

BMad plans, the factory ships.
Proof and human judgment stay in the loop.

Does this give an agent more permissions?

No. Actual host permissions and project trust apply. Prompts, hooks and local locks are conveniences; reviewer prose does not enforce an independent sandbox. Production writes require explicit human GO.

What counts as evidence?

Current subject-bound test results, independently inspected effects and actual-diff review. A declared coverage link, successful command, local done status or bare commit identity is insufficient to prove a shipped result. Failed, missing and unknown evidence remain visible.

Can I choose the model and agents?

The host determines available models and execution tools. Staffing follows capability, risk and likely rework, with a native fallback. Record requested models separately from observed effective models; unknown attribution stays unknown. The pack contains no model gateway.

What happens when a session ends?

Records and checkpoints preserve context. On resume, the host reconciles repository state, ownership, provider outcomes and evidence before continuing. Hooks assist recovery; they do not start workers. There is no pack scheduler, daemon or hosted service.

Does it monitor my project continuously?

Observation requires an available supported capability, approved source/read scope and window, attributable observations and separate repair authority. Without an explicitly authorized and observed host schedule, observation ends with the active session. Monitoring is off by default; no telemetry is added.

How does BMad fit? What about review bots?

BMad skills are central to planning structured epics and stories. Method v6 is installed separately through its official pinned installer; the pack never vendors it. Verify the actual planning capability; if unavailable, report that limit rather than imply BMad ran. Greptile, CodeRabbit, Bugbot and Copilot review integrations are optional and disabled by default. Available tooling and account access must be observed.

Can I uninstall or keep my customizations?

The installer records ownership and backups. Use its uninstall path to remove owned projections safely; edited files require reconciliation rather than destructive cleanup. The sf-evolve workflow supports reviewed overlays that survive reinstalls with drift checks and rollback evidence.

Is the skills-only route enough?

It supplies the portable skill source. It does not establish native roles, hooks, project setup, invocation controls or trust. Choose full project setup for those capabilities; plugin custom-agent registration and combined host loading have their stated limits.

Is this a released, hosted product?

This showcase describes a pre-release pack targeting v0.1.0. Release artifacts, public source availability, marketplace acceptance and Pages deployment are not established by this page. The declared repository links are publication targets pending verification. You can inspect and use an existing trusted local checkout.
