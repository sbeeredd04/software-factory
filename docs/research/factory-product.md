# Software Factory: public product research

Research date: 2026-10-15. Sources are public Factory documentation, public Factory research/product pages, and its official public GitHub repository. The factory.ai and docs.factory.ai URLs inspected redirect to factory.com and docs.factory.com; current canonical URLs are cited below. This is an original synthesis, not a reconstruction of proprietary internals. Local observations come from repository instructions, product principles, canonical skill entries and orchestration references; implementation completeness still needs the engineering audit.

## Product conclusion

Complete the portable, evidence-oriented method already described by the pack. Factory offers a useful reference for decomposition, focused contexts, independent validation, and human steering. Matching its hosted runtime, learned router, managed computers, analytics, or scheduler would change this repository's product and violate current non-goals. The distinctive attainable outcome is a consumer-controlled SDLC evidence graph operated by the host agent, with deterministic standard-library helpers preserving facts.

## What the public sources establish

1. **Documented orchestration mechanics.** Factory's architecture article describes acceptance assertions before feature decomposition, bounded workers with fresh context, shared artifacts, and milestone validation. Scrutiny reviewers inspect implementation; user-testing validators exercise behavior externally. Validators report gaps; the orchestrator creates corrective features and repeats validation. The published runner processes feature workers in order. These are a vendor account of mechanics, not an independent verification or a public implementation. [How Missions Work](https://factory.com/news/missions-architecture).

2. **Advertised scope differs from that implementation description.** The Missions product page advertises simultaneous agents, dependency coordination and multi-repository work. It does not establish a public scheduler algorithm, graph schema, conflict protocol, or equivalence with the architecture article's ordered runner. Avoid claiming that Factory documents a general concurrent DAG execution engine. [Missions product](https://factory.ai/product/missions).

3. **Planning and user control.** Missions are presented as bounded efforts with an approved plan, milestones and reused or developed skills. Scriptable application startup, input and observation are prerequisites for useful end-user validation. Validation cadence is configurable by milestone. Its simple feature-count-plus-validator-count cost heuristic is explicitly a lower bound because corrective work adds runs. [Missions overview](https://docs.factory.com/missions/overview), [Planning and Validation](https://docs.factory.com/missions/planning).

4. **Authority is separate from workflow mode.** Spec Mode investigates and asks for plan approval before edits; Normal, Spec and Mission are interaction modes. Autonomy controls, command policy, sandboxing and organization restrictions govern actions separately. This supports keeping a plan's meaning distinct from permission to execute consequences. [Interaction Modes](https://docs.factory.com/autonomy-and-safety/specification-mode).

5. **Role-specific models are documented.** Orchestrator, worker and validator models/reasoning can be configured independently; Missions inherit project instructions, skills, hooks, MCP and custom droids. The reference also exposes switches that disable scrutiny or user testing, so public documentation does not support describing every Factory validation gate as unavoidable. [Missions reference](https://docs.factory.com/missions/reference).

6. **Subagent routing has concrete precedence.** A custom droid can pin a model; otherwise complexity routing can select one, with parent fallback. Droids supply fresh context and a tool policy; skills run procedures in the current context. Model diversity and reviewer independence are distinct properties. [Custom droids](https://docs.factory.com/harness/subagents).

7. **Automatic routing is a separate runtime capability.** Factory explains that model selection belongs before prompt/tool assembly in the harness, with access to session state and outcomes. Published cost and quality gains are vendor measurements against stated baselines, not guarantees this pack could inherit. Our compatible analogue is explicit host capability selection, rationale, effective-model recording and fallback—not a Python model gateway. [Routing architecture](https://factory.com/news/model-routing-belongs-in-the-harness), [Router results](https://factory.com/news/factory-router-inference-savings).

8. **Context is an index plus selective loading.** Factory describes discovering compact capability metadata, loading full instructions and schemas when needed, and retaining loaded tools. This is relevant to the pack's short entry skills and linked references; proprietary caches and loading mechanisms are outside its scope. [Deferred Context Engine](https://factory.com/news/deferred-context-engine).

9. **Memory must preserve operational facts.** Factory's compression research describes structured incremental summaries and tests recall, artifact tracking, next steps and decisions. Its own reported artifact tracking remains weak. The transferable principle is to store file/evidence identities explicitly and evaluate continuation, rather than treating prose compression as authoritative state. [Context compression research](https://factory.com/news/evaluating-compression). Versioned repository guidance is a separate durable surface. [AGENTS.md](https://docs.factory.com/harness/agents-md).

10. **Extensions and enforcement have different owners.** Plugins bundle skills, droids, hooks and MCP settings. Hooks run at lifecycle boundaries and can affect tool handling; MCP connects external capabilities. Enforcement details belong to the actual host and operating environment, not promises inside Markdown. [Plugins](https://docs.factory.com/harness/plugins), [Hooks](https://docs.factory.com/harness/hooks), [MCP](https://docs.factory.com/harness/mcp), [Enterprise controls](https://docs.factory.com/enterprise/hierarchical-settings-and-org-control).

11. **Review and QA have inspectable integration surfaces.** Factory documents generated CI review setup, repository review guidance, dedicated security review, and QA that selects flows from affected applications. Its official public Action is inspectable; it is not the private Missions runtime. These suggest adapter contracts, scoped findings and raw-evidence links for the pack. [Code review](https://docs.factory.com/software-factory/code-review-ci), [Security review](https://docs.factory.com/software-factory/security-review), [Automated QA](https://docs.factory.com/software-factory/automated-qa), [Official Droid Action](https://github.com/Factory-AI/droid-action).

12. **Recovery includes human steering.** The CLI docs explicitly describe pausing, redirecting and replanning when execution stalls. The app documents resuming saved missions and inspecting worker progress. These establish product controls, not exactly-once semantics for external actions. The pack's reconcile-before-retry rule should remain explicit. [Running Missions in CLI](https://docs.factory.com/missions/running-cli), [Running Missions in app](https://docs.factory.com/missions/running-app).

13. **Readiness and shipping need separate claims.** Readiness evaluates repositories and applications against operational foundations. The Software Factory product page lists deployment/release and post-deploy operations, but the sources examined do not establish an auditable deployed-SHA acceptance contract for every mission. Treat that coverage as advertised scope and retain the pack's explicit release/effect receipts. [Agent Readiness](https://docs.factory.com/agent-readiness/overview), [Software Factory product](https://factory.com/product/software-factory).

## Capability gap map against current repository

- **Orchestration and dependency planning — substantially specified.** `software-factory` already describes grounding, independent plan review, a dependency-derived ready frontier, claimed worktrees, parallel eligible streams, one integration owner, deploy proof and human epic acceptance. The board is the sole live story-status source. Extend these contracts; do not add a competing runner or status graph.
- **Planning and validation — substantially specified, traceability should be audited.** `sf-eval` requires signed-off per-surface suites and stable story cases before work queues. It supports deterministic checks and declared browser/judge harnesses, with unverified outcomes for missing harnesses. Verify that every planned behavior connects to a case, execution receipt, integrated subject and applicable release proof. Preserve explicit cross-feature behavior assertions, not just individual story green checks.
- **Routing — concrete missing product surface.** `sf-agents` is a placeholder despite promised registry, risk routing, fallback, review integration and triage. Implement the smallest host capability inventory and route record. Discovery must respect this repository's prohibition on invoking agent CLIs, including version probes.
- **Onboarding — concrete missing product surface.** `sf-help` is a placeholder. It should consume `sf-crawl`, discover existing commands and proof surfaces, distinguish observed facts from defaults, prepare reviewable setup and capture material decisions. Its current fixed 20-question promise needs a product decision before changing to adaptive questioning.
- **Evolution — concrete missing product surface.** `sf-evolve` is a placeholder. Finish reviewed overlays, integration provenance and a retro-to-proposal loop with independent validation. No self-installing dependency fetches or automatic runtime updates.
- **Code context — honest bounded implementation.** `sf-crawl` documents Python AST coverage and limited JavaScript/TypeScript treatment. It already offers machine-readable output. A graph view must expose these coverage limits rather than implying complete semantic knowledge of every language.
- **Recovery — strong contract, prove failure cases.** Existing recovery notes cover stale claims, unknown external effects, actual-state reconciliation and compact checkpoints. Demonstrate interrupted-worker, stale-evidence, changed-base and uncertain-publish cases using deterministic fixtures and explicit provider observations where authorized.
- **Security — keep host boundary explicit.** Existing hard boundaries correctly call prompts/hooks/locks conveniences. Scope tool capabilities, effects and approvals in worker briefs; never represent a Python path claim or review role as a sandbox.
- **Full SDLC — model operation and feedback explicitly.** Feature and bug workflows cover planning through deployment. Ensure monitoring, incident evidence, rollback, documentation changes and follow-up product decisions can feed new board stories using existing roles/skills. A hosted alert collector, scheduler or always-on monitor remains a separate product decision.

## Recommended compatible scope

1. Finish the three placeholders within the existing eleven canonical skills; use references and small deterministic helpers instead of adding more top-level skills.
2. Treat the graph as a derived, provenance-bearing view over existing artifacts. Useful nodes: requirement/assertion, decision, epic/story, code surface, work claim, check receipt, review finding, commit/PR, deployment/effect and checkpoint. Useful edges: depends-on, covers, implements, verifies, reviews, supersedes and deployed-as. Record source anchors, subject identity/digest, observed time and confirmed/inferred/unknown confidence where appropriate.
3. Keep authoritative ownership separate: board owns story status; claims own write exclusivity; receipts own observed checks; decisions own approved scope; provider observations own external outcome. A graph may explain readiness and missing proof but must not become a second mutable source of truth.
4. Add focused answer surfaces: why is this story blocked, what can run now, what does this change affect, which requirement lacks proof, what invalidated after this base changed, what shipped, and what still needs human acceptance. Plain JSON, Markdown and the current offline dashboard can support this without a graph database.
5. Dogfood one complete representative lap plus failure/recovery scenarios. Distinguish static format checks, deterministic fixture behavior, actual host execution and actual deployment proof. Report unsupported host behavior honestly. No live host CLI execution in this repository.
6. Preserve the stronger current evidence rule: missing, unknown, failed or infrastructure-error proof never silently passes. Narrow applicability needs a scoped decision. Human acceptance closes an epic; it does not fabricate a test result.

## Material decisions for the human owner

- **Product boundary:** confirm completion of the portable pack, or explicitly authorize a separate future runtime product. Recommend the portable pack for this release.
- **Graph meaning:** a lifecycle evidence graph and architecture projection, or an autonomous scheduling/memory engine? Recommend derived views over existing records, with no duplicate status store.
- **Onboarding experience:** retain the currently promised 20-question interview or approve a shorter evidence-led adaptive interview. Recommend discovered defaults plus questions only for missing material decisions.
- **Release proof:** for this non-deployable pack, approve the exact local installation/projection and consumer-fixture equivalent to staging proof; never call a generic health check deployment validation.
- **BMad contract:** principles say BMad does planning, while canonical entry/planning explicitly allow native fallback. Recommend making optional pinned BMad plus equivalent native planning the consistent product statement, subject to owner confirmation if prior intent differs.
- **Human cadence and routing:** keep epic acceptance and new authority decisions with the owner; reuse existing scope approval. Host model availability should determine valid IDs. Recommend stronger reasoning for planning/risky implementation/independent validation and efficient workers for routine bounded work, with requested/effective route recorded.

No repository files were changed. No agent CLI, git mutation, installation, external message or runtime execution was performed for this research. This memo reports source inspection, not passed implementation tests or verified Factory internals.
